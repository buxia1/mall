# 03 · 简单 CRUD 与高价值工程

这份文档解决一个很实际的问题：**哪些活可以丢给我，哪些你必须亲手写一遍**。
判断标准不是"难不难写"，而是**写错了会不会出事、以及出什么事**。

---

## 一、判定标准

| 类型 | 信号 | 应对 |
|---|---|---|
| 🟢 简单 CRUD | 单表增删改查 + 参数校验 + 分页；错了是"功能不对"，看得见 | 交给我，你只需要 review 契约（路径/参数名/返回结构） |
| 🟡 中等 | 涉及多表关系维护、引用完整性、冗余字段重算；错了会留脏数据 | 交给我，但**事务边界和级联范围你要看懂** |
| 🔴 高价值 | 并发、事务边界、缓存一致性、幂等、失败补偿、权限边界；错了是"数据错了/超卖了/权限漏了"，且**测试很难发现** | **你亲手写**，我出设计、写测试、做破坏性实验配合你 |

🔴 的共同特征：**正确性依赖时序或并发**，而不是依赖"代码写全了没有"。

## 二、模块 2 的接口分级（已完成的 40 个）

| 接口组 | 分级 | 说明 |
|---|:-:|---|
| `/admin` register / list / {id} / update / updatePassword / delete / updateStatus | 🟢 | 单表 CRUD。`update` 里"不传密码就保持原值"是唯一的细节点 |
| `/admin/role/update` | 🟡 | 关系重建 + 受影响角色 `admin_count` 重算 + 清权限缓存 |
| `/admin/role/{adminId}` | 🟢 | 一次关联查询 |
| `/role` create / update / list / listAll / updateStatus | 🟢 | 单表 |
| `/role/delete`（批量） | 🟡 | 要级联删菜单/资源/管理员三张关系表，漏一张就留脏数据 |
| `/role/allocMenu` | 🟡 | 先删后插，要事务；但菜单不参与 URL 鉴权，**不需要**清权限缓存 |
| `/role/allocResource` | 🔴 | 改的是"谁能访问什么"，**必须清权限缓存**，而且要在事务提交之后清 |
| `/role/listMenu` `/listResource` | 🟢 | 关联查询 |
| `/menu` 全部（含 `treeList`） | 🟢 | `treeList` 只是内存里组树，一次查库比递归查库好 |
| `/resource` create / update / delete | 🔴 | 代码只有几行，但**清缓存是接口契约**；漏了就是"新加的资源要等缓存过期才生效" |
| `/resource` {id} / list / listAll | 🟢 | 查询 |
| `/resourceCategory` 全部 | 🟢 | 纯 CRUD，连缓存都不用管 |

**结论：模块 2 的含金量不在 CRUD，在两件事**——
① 鉴权链路（JWT + Redis 双写、动态 RBAC）；② 缓存失效的边界与时机。
CRUD 那 40 个接口是体力活，真正值得你花时间的是 [02 文档](02-模块1和2的设计与取舍.md)里的 D7–D9。

## 三、后续模块的含金量地图（这才是重点）

### 模块 3 · 商品（6 张表，下一个做）

| 接口 | 分级 | 难在哪 |
|---|:-:|---|
| `/product/create`、`/product/update/{id}` | 🔴 | **跨多表事务**：`pms_product` + `pms_sku_stock` + `pms_product_attribute_value` + 阶梯价/会员价。`PmsProductParam` 是 `PmsProduct` 的超集，一次提交一堆子表。写漏一张表就是"商品建了但 SKU 没有" |
| `/product/updateInfo/{id}` | 🟡 | 要把散在 4 张表的数据拼成一个 `PmsProductResult` |
| `/product/list`（8 个筛选条件） | 🟢 | 动态 SQL + 分页 |
| `/product/*Status` 5 个批量改状态 | 🟢 | 批量 update。注意 `deleteStatus` 是**软删**（这表和用户表不同，它有 `delete_status` 字段） |
| `/product/detail/{id}`（前台） | 🔴 | **D10/D11 的落地点**：商品详情缓存。要处理穿透（查不到别缓存 null）、击穿（热点 key 重建）、雪崩（过期时间打散），以及"改了商品名详情要返回新名字"的一致性 |
| `/brand/*`、`/productCategory/*`、`/productAttribute/*`、`/sku/*` | 🟢 | 基本是 CRUD；`list/withChildren` 和 `attrInfo` 是拼装查询 🟡 |

### 模块 4 · 会员（2 张表）

| 点 | 分级 | 难在哪 |
|---|:-:|---|
| `/sso/*` 注册登录 | 🟡 | 和后台登录是**两套完全独立的体系**：不同表、不同接口、**token 不能互用**。这是个容易踩的坑——共用一套 JWT 工具，就容易让会员 token 访问到后台接口 |
| `/memberLevel/list` | 🟢 | CRUD |

### 模块 5 · 购物车与下单（4 张表，⭐ 面试主战场）

| 点 | 分级 | 难在哪 |
|---|:-:|---|
| `/cart/*` | 🟢 | 加购、改数量、删除、列表，单表 |
| `/cart/list/promotion` | 🟡 | 带促销计算的购物车视图 |
| `/order/generateConfirmOrder` | 🔴 | **D12 加购价 ≠ 下单价**：确认单只是"算钱"，不落库、不扣库存。价格必须在**这一刻**重新算，不能用加购时的价格 |
| `/order/generateOrder` | 🔴🔴 | **D15 事务边界**：建订单 + 明细 + **锁库存** + 清购物车 + 关联券 + 发延迟消息，全部要在一个事务里；事务外的动作（发 MQ）失败怎么补偿 |
| 扣库存 | 🔴🔴 | **D13 防超卖**：`UPDATE ... SET stock = stock - #{qty} WHERE id = ? AND stock >= #{qty}`，靠**条件更新的影响行数**判断成败，不是先查后改 |
| `/order/cancelTimeOutOrder` | 🔴🔴 | **D14 订单超时取消**：延迟消息 + **定时任务兜底**（`oms_order_setting.normalOrderOvertime` 读超时时间，不是硬编码）。要回滚库存、积分、优惠券 |
| `/order/paySuccess` | 🔴 | 支付回调**必须幂等**（同一订单重复回调不能重复加积分/重复改销量） |
| `/order/*` 管理端查询发货关闭 | 🟡 | 多条件分页 + 批量 |

**`04-开发顺序与验收.md` 要求的破坏性实验**（比读代码有用十倍，到时候我会准备好脚本）：
JMeter 并发下单会不会超卖；下单后停掉 RabbitMQ 订单还能不能取消；
停掉 Redis 报什么错、有没有降级；下单中途 kill 服务数据一致吗。

## 四、建议的分工

| 谁 | 做什么 |

## 五、17 道决策题 · 自测索引

`03-技术决策清单.md` 里的题是贯穿全程的，要求"不看资料能讲出来"。
已完成模块对应的 D1–D9 答案要点在 [02 文档](02-模块1和2的设计与取舍.md)里，
你可以拿下面这些问题自测：

**D1–D6（基础层）**
- 统一返回体为什么用静态工厂而不是公开构造器？
- 业务异常为什么不继承 `Exception`？
- 全局异常处理器漏了 `Exception` 兜底会怎样？（提示：whitelabel 错误页）
- `CommonPage` 为什么要适配两种分页模型？
- Redis 的 key 和 value 分别用什么序列化，为什么？
- 日志切面为什么必须用 `@Around`？

**D7–D9（认证鉴权）**
- JWT 已经能验身份了，为什么还要 Redis？（提示：可撤销）
- Redis 的 key 为什么用 `SHA-256(token)` 而不是原文？
- 权限为什么不用 `@PreAuthorize`？（提示：数据在库里，要立刻生效）
- 权限缓存的**失效时机**为什么必须和资源 CRUD 绑在一起？
- `refreshToken` 为什么只续 Redis TTL、不重新签发 JWT？

**D10–D17（待做）** —— 商品缓存、穿透/击穿/雪崩、加购价与下单价、防超卖、
超时取消、事务边界、秒杀为什么要 Redis+MQ、优惠券怎么算。
做到对应模块前先自己想，别翻答案。
